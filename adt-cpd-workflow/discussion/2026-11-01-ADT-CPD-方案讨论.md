### 助手

「自动化任务」是 StarMind 的定时任务与提醒中心（内部叫 `schedules`）。它本质上只做一件事：**到点后把一条预先写好的指令投递回它原来所属的那个会话，让我在原会话里执行一轮**。它并不是独立运行的后台脚本，因此任务产生的上下文、文件和结论都留在原会话里。

## 在哪里能看到它
- **左侧栏「自动化任务」页**：这是全局的任务总览，打开它不会选中或激活任何会话
- **右侧栏的任务页签**：这是同一个任务在会话上下文里的详情视图
- **会话页头的时钟图标**：只在当前会话确实有活动提醒时出现（只有 1 条时直接打开详情，多条时弹出浮层，逾期在前）
- **对话里的任务卡片**：我在会话中创建任务时，该轮会产生一张卡片
- 侧栏中带有活动任务、未归档且空闲的会话，其行上还会显示一个时钟标记

## 能做什么
- 搜索；按 **全部 / 已开启 / 已结束** 筛选
- 在「规则」里修改任务名称、指令和运行时间
- 查看「任务运行记录」（每次投递的时间与状态）
- 删除任务（需二次确认，**硬删除**，连保存的运行记录一起删；原会话和已排队消息保留）、一键「清除全部已结束任务」、跳到原会话

## 时间规则
一次性（唯一时刻）、每 N 秒、每 N 分钟、每小时、每天、周一到周五、每周、自定义五段式 cron；可以指定 IANA 时区（默认跟随系统）。

## 两个容易踩的点
1. **页面上的「新建」只是打开一个新会话**，页面里没有创建表单——任务是由你在对话里用自然语言提出（例如“每天早上 9 点提醒我检查昨天的构建”），再由我调用 schedule 工具创建。
2. **不支持暂停或立即执行**；已结束的任务只读，不能改时间。另外，由子 agent 委派产生的工作会话不能设置提醒（在服务层就被拦住）。停机期间错过的多次重复提醒，恢复后只会补投最近一次。

需要的话，我现在就可以在某个会话里帮你建一个，比如每天固定时间做一件事、或者 N 分钟后提醒你。

### 助手

我先把这个问题拆成四层，你就能看清 StarMind 里该动哪些零件：**环境层（代码在哪跑）· 工具层（怎么跑起来）· 流程层（谁决定下一步）· 知识层（agent 怎么知道该跑什么）**。你们现在 opencode 里那套东西，正好一层不落地能映射过来，但**不能照搬，尤其 LangGraph 不要重写**。

## 一、opencode → StarMind 的概念映射

| opencode 现有资产 | StarMind 对应机制 | 迁移要点 |
|---|---|---|
| ADT/CPD 的 SKILL.md | **原生 Skill**，格式几乎一样 | 目录 bundle `<name>/SKILL.md`，YAML frontmatter 必填 `name`(kebab-case) + `description`，可选 `whenToUse` / `user-invocable`。放到 `<repo>/.dsh/skills/` 或 `<repo>/.agents/skills/`（项目级），或 `C:\Users\Administrator\.dsh-beta\skills\`（本机用户级）。**只发现一层**，`a/b/SKILL.md` 里的嵌套不认。要改的主要是正文里的工具名：`bash` → `pwsh` / `rw_exec` |
| opencode subagent（独立提示词+模型+工具白名单） | **子 agent**（`subagent` 一次性 / `subagent_fork` 带上文） | 提示词可原样搬；工具面用 profile/权限预设控制，而不是每个子 agent 挂白名单 |
| langgraph 节点编排 | **不动它**，服务化后挂成工具 | 用内置 `dsh-mcp-client` 把它封成 MCP server（工具名 `mcp__cpdflow__next_stage` 这种），状态机、重试、人工暂停都留在 Python 里 |
| opencode 里的"一次性扇出"编排 | `workflow` 工具（JS 脚本，`pipeline`/`parallel`/`phase`） | 只在"无长等待、状态少"时用它重写，别把 langgraph 的持久状态往这里塞 |
| artget 拉背景包 | 插件工具 或 skill 里的固定命令 + 校验脚本 | 关键是**可校验**：版本 + 安装路径 + 指纹，让 agent 先验后跑 |
| 长编译、整夜回归 | **自动化任务**（定时任务投递回原会话） | 不要让模型干等一个 40 分钟的编译 |

## 二、环境层：把"三种环境"变成"三种会话根目录"

这是你们真正的难点，也是 StarMind 比 opencode 强的地方——**它自带远程工作区能力**（本客户端已装好 `rw_*` 工具集：`rw_connect` / `rw_pick_workspace` / `rw_exec` / `rw_sync` / `rw_push` / `rw_forward`）。

- **Windows 写码 + Linux 测试**：本地会话 + `rw_connect` 到测试机 → `rw_pick_workspace` → `rw_exec` 编译/起界面 → `rw_push` 推改动 → 截图回流。人不用离开一个界面。
- **Linux 写码 + Linux 测试**：直接把会话开在远程工作区，Windows 只当终端。
- **单一事实源永远是 git**，别指望双向文件同步当主线：`rw_sync` 是有界的（默认深度 8、2000 文件），Qt 大仓一键全量镜像必炸。用"远程 clone + 按需读取 + 局部上传"。
- **背景包刻意排除在镜像之外**：artget 装到远程固定路径（如 `/opt/bgpack/<ver>`），工作区里只留一个 `bgpack.json`（版本、校验和、安装时间、由谁装）。agent 每次启动先读它、校验、不一致就重拉。这条能省掉你 90% 的"为什么我这儿跑不起来"。

## 三、流程层：把"能自动跳"和"必须停"分开

阶段阶梯建议照这个写，每级一个**门**（gate）：

```
环境体检 → 拉代码/校验背景包 → 编译 → 单测+静态检查 → GUI 冒烟(截图) → 上下位机联调 → 打包交付
```

- **门 = 脚本，不是模型的判断**：每阶段一个脚本吃参数吐 JSON（`{ok, artifacts, evidence_path}`），agent 只读结论。这比让 LLM 自己看日志判断"编译过了没"可靠一个数量级。
- **需要人审的节点留给 langgraph**（挂 MCP 回来），纯扇出的（多模块并行编译、ADT/CPD 双矩阵）用 `workflow`。
- **危险动作走审批**：下位机烧写、发布上位机版本、切换背景包版本——这些必须弹人工确认，别让 agent 自己决定。

## 四、QT 界面在 Linux 上的实测要点

- 无头：`Xvfb :99` + `QT_QPA_PLATFORM=xcb`（或 `offscreen` 做非渲染逻辑测试），截图用 `xwd`/`import`/`grim`，图直接回会话里让我看——这样"界面有没有改对"就变成我可验证的事项。
- 上下位机：**测试台固定机**（硬件在环）+ 串口/telnet 用 `rw_forward` 打通；测试台单独一个 profile（允许的命令、模型、权限都定死）。
- 现场机和测试环境必须网络互通，否则联调阶段永远要人肉搬。

## 五、交付形态：一个内部插件包 + 一套 skill

```
@corp/dsh-qt-workflow/        ← npm 包，内网 registry 或 file:tarball 离线装
├── skills/adt-env/SKILL.md      环境事实（机器、路径、背景包、启动命令）
├── skills/adt-flow/SKILL.md     阶段阶梯 + 每个门的判定标准
├── skills/cpd-flow/SKILL.md
├── lib/                         背景包校验、阶段门、截图对比等工具
└── AGENTS.md 片段               仓库级约定（编译命令、禁止事项）
```

用 `plugin_manager` 的 `install_bundle` 一次装进所有开发者的 desktop profile，升级可控、版本可锁。过渡期也可以先放共享目录走 `customSkillDirs`，但最终要收进包里，否则 30 个人 30 个版本。

## 六、建议的落地顺序（2–3 周出可用 MVP）

1. **Day 1｜打通一条链路**：一台 Linux 测试机 + 一台测试台接进 `rw_connect`，手动跑通 artget → 编译 → 起界面 → 截一张图。
2. **Day 3–5｜搬 skill**：opencode 的 SKILL.md 原样复制进来，补一个 `adt-env` 把上面这些环境事实写死（这是投入产出比最高的一步）。
3. **Week 2｜阶段门 + ADT 端到端 demo**：从拉包到冒烟截图，**一个会话里跑完**，记录人工介入次数。
4. **Week 3｜CPD 复制 + langgraph 挂 MCP**，人工节点接回来。
5. 度量就看两个数：**端到端人工介入次数**、**改完代码到看见界面截图的时间**。

## 七、需要提前确认的坑

- **模型通道**：整个流程在内网 — 这台客户端能不能出网访问模型 API？不能的话要先解决（放行域名 / 内网网关 / 私有部署端点），否则一切免谈。顺带确认代码出内网的合规口径。
- **凭据**：SSH key、artget 账号**不要**写进 AGENTS.md、skill 或工作区；用远程机器注册表 + 系统凭据。
- **沙箱边界**：默认 `workspace-write`，只有工作区内可写；给每个项目固定一个 workspace 根，别指望 agent 跨盘写文件。
- **仓库内容视为不可信输入**：别人 PR 里的注释也可能是指令。
- **版本漂移**：客户端还是 beta，插件 ABI 会变，内部包锁版本、留回滚。

### 助手

设计方案已写入 [ADT-CPD_StarMind_开发流程设计方案.md](ADT-CPD_StarMind_开发流程设计方案.md)，另附可直接运行的骨架：[devgate](skeleton/devgate)、[adt-env/SKILL.md](skeleton/skills/adt-env/SKILL.md)、[bgpack.lock.json](skeleton/bgpack.lock.json)。

下面是我做出 **五个关键判断** 的理由，也是评审时最值得争论的地方。

## 1. 执行环境：三种形态，只选一个因素

| 形态 | 适用 | StarMind 机制 |
|---|---|---|
| 远程镜像会话 | Windows 写码 → Linux 测 | `rw_connect` + `rw_pick_workspace`，cwd 落在本地镜像 |
| 远程整机界面 | Linux 写码、整夜值守 | 在 Linux 上跑 `dsh web`，经 SSH 隧道搬到本机标签页，**不开任何外部端口** |
| 本地会话 + 远程执行 | 偶尔只看一眼 | `rw_exec` / `rw_read_file`（本地会话只暴露 3 个 `rw_*`） |

第三种形态是本方案最有价值的一处简化：**同一套 skill、同一套门禁，在 Windows 会话里跑，和在 Linux 整机上跑，是同一份**，不需要为两种习惯维护两套流程。

## 2. 把“过没过”交给脚本，把“为什么”交给模型

这是我认为你们现在 opencode 那套里最该改的一点。模型判断“编译过了没”必然有假阳性。方案里定义了一个 `devgate` CLI，用退出码区分四种语义：

`0 通过 / 1 代码问题 / 2 要人 / 3 环境问题`

第 3 码尤其重要：它把“背景包没装”和“代码写错”分开，模型就不会在环境坏掉时白改半小时代码。

## 3. 门的凭证绑定 commit，防止“过门后再改一行”

`.devstate/gates.json` 里每条凭证带 `commit` + `bgpack 版本`。后续阶段启动前复验，不一致即过期。这样“绿灯发布”在机制上不成立，不需要靠人盯。

## 4. LangGraph 不搬进 StarMind，包成 MCP

结论在文档第 9 节：**不重写图**。用内置 `dsh-mcp-client` 把图封成 4 类操作（查状态/推进/提交结论/等人批准），模型看到的是 `mcp__cpdflow__*`。判定标准一句话：*这个阶段会不会停在等人超过 10 分钟、或需要跨天恢复？会 → 进图；不会 → 留在会话。*

反向通道（LangGraph 主动驱 StarMind）用 ACP 的 `dsh --profile acp`，定位是无人值守批处理，不用于交互开发。

## 5. 人跑 / AI 跑 / CI 跑，是同一套

`dsh --profile headless --permission-mode workspace-write --approval-policy never --json` 在构建机上跑，退出码直接当 CI 结果。只要 `devgate` 写对了，三者结果一致——这是把 AI 引入生产流程时最需要的**可回退性**。

1. 把 `gh` 和 `ssh` 都试过一遍，都没有用；但 **Windows 凭据管理器里其实存着 `git:https://github.com` 和 `gh:github.com:Madelining` 两条凭据**。
2. git 的凭据助手 `git-credential-manager` 要启动子进程才能读取凭据库，被沙箱拦成信号管道失败，`spawn EPERM`；提权后就通了。
3. 加 `-c http.sslBackend=openssl` 绕开 schannel。

`gh` 那边还是未登录状态，但 **git 本身已经能读写这个仓库了**，不影响推送。
